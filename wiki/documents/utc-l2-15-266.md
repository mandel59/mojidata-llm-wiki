# L2/15-266

## 要約

John H. Jenkins が、品質にばらつきのある `kZVariant` データの全面置換と定義の明確化を提案した。
ISO/IEC 10646 Annex S の source separation 例と、既知の統合誤りを新データの根拠にする。
本文末尾の統合誤り一覧は未記入であり、完成した置換データや UTC の決定ではない。
本文日付は2015-10-26、registry 日付は2015-10-29。後に [L2/19-015](utc-l2-19-015.md) が本提案を置き換えた。

## 提案内容

- 通常なら統合可能な字形が source separation rule、non-cognate rule、統合処理の誤りによって別々に符号化された場合を、field description に含める。
- 既存データを全面置換し、Annex S §S.3 の例と既知の統合誤りから構成する。本文は Annex S 由来とする文字群を列挙する。
- A→B、B→C なら A→C となる推移性と、A→B なら B→A となる対称性を確保する。原文は後者を “reflexive” と呼ぶが、示された条件は対称性である。
- 末尾の「既知の統合誤り」欄は追加予定のままで、具体的な一覧を提供していない。

## 後続決定

改訂提案は [L2/19-015](utc-l2-19-015.md)、見直し理由の詳細は [L2/19-186](utc-l2-19-186.md) を参照。Unicode 13.0 の実際の変更は [確定データの見直し event](../events/unicode-13-kzvariant-data-overhaul.md) にまとめる。

## 論点

non-cognate rule を含めるこの旧提案の定義を、後の確定仕様へそのまま転記しない。2019年の ad hoc report と Unicode 13.0 の UAX \#38 は、同じ abstract shape と同じ semantics を持つ関係として説明する。定義の変遷は [kZVariant](../topics/kzvariant.md) を参照。
